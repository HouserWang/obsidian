你之所以会“当时一看就懂，过几天就忘”，是因为市面上的秒杀和库存方案大多在堆砌“技术名词”（如 Redis, MQ, 限流, 降级），却没有给你一个**统一的、符合本能的思维骨架**。

站在架构师的第一性原理来看，秒杀和库存的核心矛盾只有一个：**“极端的写并发流量，击穿了数据库单行记录（热点行）的 I/O 极限。”**

只要你抓住这个核心，任何秒杀和库存的设计都可以归纳为一个极其简单的**“漏斗模型”**与**“热点行消除术”**。把下面这个思维框架存入你的 Obsidian，以后面试官只要问到这两个问题，你闭着眼睛都能顺着这根线答出高分方案。

# 🧠 万能思维骨架：三步漏斗法 (The Funnel Model)

秒杀系统本质上就是一个“漏斗”，我们的核心目标是：**层层拦截，把高并发读写请求在到达数据库之前消灭掉 99.9%。** 参考[[限流与熔断|限流]]。

```text
       [100W qps]  ===========================>  1. 边缘层 (CDN / 网关) : [[限流与熔断|限流]]与动静分离
                     \                      /
                       \   [1W qps]        /
                         ==================     2. 缓存层 (Redis Lua) : 状态控制与库存预扣
                           \            /
                             \ [100 qps]
                               ==========       3. 存储层 (MySQL DB)  : 异步写盘与热点行消除
```

# 📝 笔记一：秒杀系统架构设计 (Seckill Architecture)

### 📌 架构第一性原理
秒杀的本质是**高并发读（占 99%）与极少量写（占 1%）的冲突**。
通过**“动静隔离”**把读流量留在边缘，通过**“异步化”**把写流量拉平，通过**“物理隔离”**保护核心交易链路。

---

### 🔍 核心技术细节与落地

#### 第一步：边缘层拦截（非核心流量过滤）
1.  **动静分离 (Static/Dynamic Isolation)**：
    *   秒杀商品的详情页、JS/CSS、图片全部静态化，直接推送到 **CDN**。
    *   用户刷新页面时，99% 的请求在 CDN 边缘节点就被拦截并返回，根本不触达你的服务器。
2.  **网关限流与防刷 (Gateway Throttling)**：
    *   通过用户 ID/IP 维度在网关层（如 Nginx/Kong）做滑动窗口限流。
    *   秒杀接口使用“动态 URL”（下单时才从后端获取加密 Token，防止脚本抢跑）。

#### 第二步：缓存层预扣（核心状态判定）
*   **Redis Lua 脚本**：这是秒杀系统的“黄金搭档”。利用 Redis 单线程执行 Lua 脚本的原子性，完成两件事：
    1.  **防重入（[[幂等性 (Idempotency)|幂等性]]）**：用 `SETNX` 判定用户是否已经抢过。
    2.  **库存预扣**：`DECRBY` 库存。如果扣减后仍 $\ge 0$，代表抢到了，返回成功。
*   **本地缓存（Local Cache）双重保险**：
    *   在 JVM 内存中维护一个 `ConcurrentHashMap`，存储一个 `isSoldOut`（是否售罄）的 Boolean 标记。
    *   一旦 Redis 扣减至 0，通过消息队列或配置中心广播通知所有应用实例将本地 `isSoldOut` 设为 `true`。后续请求在 JVM 内存中就被直接拒绝（**Fast-Fail 快速失败**），连 Redis 都不用查。

#### 第三步：存储层落盘（异步最终一致）
*   **MQ 削峰填谷**：参考[[限流与熔断|削峰]]。
    *   Redis 预扣成功的请求，代表已经“拿到了购买资格”。此时不直接写库，而是发送一条“秒杀订单创建”的消息到 MQ。
    *   消费端以数据库能承受的速率（如 500/s）慢慢消费 MQ，完成真实的订单创建、扣减 MySQL 库存、生成支付单。
*   **物理隔离 (Domain Isolation)**：
    *   秒杀的数据库和微服务集群必须与普通的“核心商品/交易系统”物理隔离，防止秒杀流量把普通用户的购物车或支付功能拖垮。

---

### 🎙️ 30秒秒杀架构 Elevator Pitch
> “秒杀系统的本质是**‘读写极度不对称的漏斗模型’**。
> 
> 在设计上，我主要采取**两层隔离与一层削峰**：
> 首先是**动静隔离**，将详情页推送到 CDN，99% 的读流量留在边缘；
> 其次是**物理隔离**，将秒杀服务与核心交易数据库独立部署，防止雪崩。
> 在写路径上，我们使用 **Redis + Lua 脚本**进行原子性的幂等校验和库存预扣，预扣成功后投递到 **MQ 削峰填谷**，由消费端异步落盘创建订单。
> 这样，真正的写库流量被压缩到了极低且平稳的水平，保障了系统的稳定性。”

# 📝 笔记二：高并发库存扣减设计 (High-Concurrency Inventory)

### 📌 架构第一性原理
库存扣减的痛点是 **“超卖（Overselling - 资损）” 与 “少卖（Underselling - 体验差）”**。
技术上的核心瓶颈在于：**高并发下，MySQL 针对单行记录（热点行）的更新，会由于数据库行锁（Row Lock）排队导致连接池瞬间爆满。**

---

### 🔍 四大库存扣减模式对比与演进

```text
+-----------------------------------------------------------------------------------------+
|                              Inventory Deducting Evolution                              |
+-----------------------------------------------------------------------------------------+
| 1. DB 悲观锁 (SELECT ... FOR UPDATE)    | 2. DB 乐观锁 (WHERE stock >= 1)                 |
|   - 缺点: 串行排队, 连接池雪崩。          |   - 缺点: 高并发下大量失败, 热点行锁依然存在。 |
|                                       |                                                 |
| 3. Redis Lua 预扣 + 异步同步 DB        | 4. 库存分片 (Inventory Sharding)               |
|   - 优点: 性能极高, 无锁。                |   - 优点: 消除热点行锁, 支持极致吞吐。          |
+-----------------------------------------------------------------------------------------+
```

#### 模式 1：MySQL 悲观锁 —— 绝大多数公司的起步（金融级绝对安全）
*   **具体实现**：
    ```sql
    START TRANSACTION;
    SELECT stock FROM t_inventory WHERE sku_id = 123 FOR UPDATE; -- 加写锁
    -- 判断库存是否足够 --
    UPDATE t_inventory SET stock = stock - 1 WHERE sku_id = 123;
    COMMIT;
    ```
*   **细节解剖**：这是最直观的事务写法。但在高并发下，所有线程都在 `FOR UPDATE` 那一步排队，等待事务提交。数据库连接池会迅速耗尽，系统出现假死。
*   **适用场景**：并发量低、对数据准确性有极端要求的系统。

#### 模式 2：MySQL 乐观锁 —— 防超卖的工业标准
*   **具体实现**：
    ```sql
    UPDATE t_inventory SET stock = stock - 1 WHERE sku_id = 123 AND stock >= 1;
    ```
*   **细节解剖**：不使用 `FOR UPDATE`。直接利用 MySQL 原生的单条 SQL 原子性进行“无锁扣减”。如果影响行数（`affected_rows`）为 1，代表扣减成功；为 0 代表库存不足。
*   **解决少卖（退款释放）**：订单超时未支付，必须加回库存：
    ```sql
    UPDATE t_inventory SET stock = stock + 1 WHERE sku_id = 123;
    ```
*   **适用场景**：并发量中等、商品热度分布均匀的电商系统。但在超大流量单品（热点行）下，依然会有严重的行锁等待。

#### 模式 3：Redis Lua 预扣 —— 大厂主流高性能方案
*   **具体实现**：
    *   在 Redis 里存放库存：`SET sku_123_stock 100`。
    *   扣减时执行 Lua 脚本：
        ```lua
        local key = KEYS[1]
        local val = tonumber(redis.call('get', key))
        if val >= 1 then
            redis.call('decrby', key, 1)
            return 1 -- 成功
        else
            return 0 -- 库存不足
        end
        ```
*   **如何防少卖（数据一致性）**：
    *   用户下单未支付，或者取消订单，必须执行 Lua 脚本将 Redis 库存加回去。
    *   在支付成功或超时释放后，通过 MQ 异步去扣减 MySQL 的真实库存。
*   **深度权衡（核心坑点）**：
    *   如果 Redis 挂了或主从切换，导致预扣数据丢失怎么办？
    *   **架构师妥协方案**：Redis 只做“购买资格校验”，MySQL 中的库存才是“最终物理真理”。如果发生 Redis 数据丢失，允许少量的“重试购买”或“退款”，通过业务层容错（发无门槛券/退款补偿）来对冲技术复杂度。

#### 模式 4：库存分片 ([[Sharding & Partitioning (分片：分区)|Inventory Sharding]]) —— 极致的“热点行消除术”
*   **具体实现**：
    *   将热卖商品 `SKU_123` 的 1000 个库存，拆分存储到多条数据库记录或多个 Redis Key 中。
    *   比如分成 5 个分片：`SKU_123_1` (200), `SKU_123_2` (200) ... `SKU_123_5` (200)。
    *   客户端请求来时，通过 `Hash(userId) % 5` 路由到不同的分片进行扣减。
*   **深度权衡**：
    *   **优点**：将原本针对单行记录的并发锁，分散到了 5 条不同的记录上。**热点行锁瓶颈直接降低为原来的 1/5**，吞吐量暴增。
    *   **缺点**：业务复杂度陡增。如果分片 1 没库存了，分片 2 还有，需要支持“跨分片路由扣减”的退避和重试逻辑。

---

### 🎙️ 30秒库存设计 Elevator Pitch
> “库存扣减的核心技术痛点是**数据库的热点行锁排队**。
> 
> 在架构演进上，我通常会经历三个阶段：
> 1.  在**中低并发**场景，使用**MySQL 乐观锁**（`SET stock = stock - 1 WHERE stock >= 1`），简单高效且绝对防超卖；
> 2.  在**高并发**场景，升级为**Redis Lua 脚本做预扣减**，将写压力从关系型数据库转移到内存数据库，再通过 MQ 异步同步 MySQL 的最终状态；
> 3.  如果遇到**极致的热卖大单品**，我会采用**库存分片（Inventory Sharding）**技术，将单行物理记录拆分为多个子记录，利用 Hash 路由分摊并发锁，从根本上解决热点行锁导致的连接池雪崩问题。”

### 💡 为什么这样记不容易忘？
下次被问到秒杀或库存：
1.  脑海里浮现 **“漏斗模型”** -> CDN (动静隔离) -> Redis (预扣) -> MQ (削峰) -> DB。
2.  脑海里浮现 **“热点行锁”** -> 悲观锁太慢 -> 乐观锁防超卖 -> Redis Lua 异步写 -> 极致情况用库存分片分散锁。

这两张图就像外键一样，会死死锁住你的技术细节，面试时只要顺着这个脉络讲，逻辑就会极度清晰。

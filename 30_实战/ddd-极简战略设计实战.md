## 【领域速模】需求：用户下单

### 1. 领域事件（发生的所有事）
- 订单已提交
- 订单已支付成功
- 库存已扣减
- 积分已发放
- 订单已发货

### 2. 触发动作
- 订单已提交 ← 用户点击下单
- 订单已支付成功 ← 支付回调
- 库存已扣减 ← 订单已支付成功
- 积分已发放 ← 订单已支付成功
- 订单已发货 ← 运营点击发货

### 3. 聚合识别
- 订单聚合：订单ID、状态、商品列表、金额
- 库存聚合：商品ID、当前库存量
- 账户聚合：用户ID、积分余额

### 4. 上下文划分
- 交易上下文：订单聚合、库存聚合
- 营销上下文：账户聚合、优惠券聚合
- 履约上下文：发货聚合、物流信息

### 5. 通信方式
- 交易→营销：通过 OrderPaid 事件
- 营销→交易：提供查询订单总额的接口
- 履约→快递100：防腐层

## 一、通用语言：顺手建个词汇表

**不搞大张旗鼓的“事件风暴”，你一个人就做这件事：**

拿到 PRD 后，打开一个 Markdown 文件，就叫 `xxx领域词汇表.md`，和代码放一起。

**具体做法：**
1.  **抓核心名词**：PRD 里反复出现的词。
    - 产品写的是“商品”，代码里就别叫 `Product`，就叫 `Goods`。
    - 产品写的是“作废”，代码方法就叫 `cancel()`，别叫 `invalidate()`。
2.  **抓易混淆动词**：一个词多个意思的，立刻记下来。
    - “取消订单”和“撤销合同”，产品说这俩是两回事？记下来，代码方法名一个叫 `cancelOrder`，一个叫 `revokeContract`，从此不混。
3.  **直接反映到代码**：包名、类名、方法名全部用词汇表里的词。

**产出物**：一个50行不到的 Markdown 文件。你一个人做，十几分钟搞定。但以后任何新人看代码，或者你自己忘了业务，看到这个词汇表立刻秒懂。

## 二、界限上下文：用三句话就划出来

**不需要画 UML，不需要装模作样的工具，就对着 PRD 问自己三个问题：**

**问题1：这个模块里，同一个词是不是有完全不同的意思？**
-   PRD 前半段说“用户”指买家的登录账号、手机号。
-   PRD 后半段说“用户”指卖家的收款方式、银行卡号。
-   **判断**：这是两个上下文了：**买家用户中心** 和 **卖家账户中心**。

**问题2：这两个模块的数据，是不是有完全不同的生命周期？**
-   “订单”一旦支付完成，就进入“不可修改”的历史状态。
-   “收货地址”是可以随时增删改的，而且删了完全不影响历史订单。
-   **判断**：**订单上下文** 和 **地址簿上下文**，一定是两个。

**问题3：这个模块的改动频率，是不是跟其他模块完全不在一个节奏上？**
-   物流模块因快递公司接口变化，一个月改三次。
-   商品类目半年不变。
-   **判断**：**物流上下文** 独立出来，改它的时候绝对不去碰商品代码。

**产出物**：你在 PRD 上直接用笔圈几块，或者在你的词汇表末尾加一行注释：

> 本项目暂定为以下上下文：
> - 订单上下文（订单、支付、取消）
> - 商品上下文（发布、上下架、库存扣减）
> - 用户上下文（个人资料、实名认证）
> - 物流上下文（发货、签收、快递100对接）

这个过程，一个人认真做，半小时。

## 三、上下文映射：只问“谁给谁数据”

上下文划出来后，开始看它们之间怎么协作。**就记三个最有用的关系，其他别管：**

**1. 防腐层——专门用来隔离“脏系统”**
你要对接一个外部物流接口，或者公司内部一个老得掉渣的 ERP，它的字段又乱又丑。
**做法**：在你的物流上下文里，建一个 `infrastructure` 包，里面写一个 `LogisticsAdapter`，把这个脏接口返回的 `String`、`Map` 全部翻译成你自己的领域对象 `ShipmentStatus`、`TrackingNumber`。**你的核心领域代码永远不 import 那个外部 SDK 的任何类。**

```java
// 你的领域值对象
public record TrackingInfo(String trackingNumber, ShipmentStatus status) {}

// 防腐层：把所有脏活关在这里
@Service
public class LogisticsAdapter {
    private final Kuaidi100Client client; // 这是外部SDK

    public TrackingInfo query(String orderId) {
        Kuaidi100Response raw = client.query(orderId);
        // 把乱七八糟的 raw.get("data").get("routes") 翻译成 TrackingInfo
        return convert(raw); 
    }
}
```

**2. 共享内核——自己人之间，少量、严谨地复用**
订单、支付、营销都依赖 `OrderStatus` 枚举和 `Money` 值对象。那就把它们抽到一个公共包 `common-kernel` 里。**但这里面的东西改了，你必须知道会影响所有上下文，所以要极其克制地往里加东西。**

```java
// 在 common-kernel 里，就放这些跨上下文通用的极简对象
public enum OrderStatus { NEW, PAID, CANCELLED, SHIPPED }
public record Money(BigDecimal amount, Currency currency) {}
```

**3. 事件驱动——用一条消息通知别人，各管各的**
订单支付成功后，要通知发积分、通知发券、通知通知系统。
**做法**：订单上下文在 `Order.pay()` 方法里，只做两件事：`this.status = PAID` 和 `publishEvent(new OrderPaidEvent(this.id))`。
**至于积分怎么发、券怎么发，订单上下文完全不知道。** 由积分上下文、营销上下文的**应用服务**监听这个事件，各自在自己的领域里操作。这也是你最熟悉的 CQRS 思维。

```java
// 订单聚合内
public void pay() {
    if (this.status != NEW) throw new OrderException("状态非法");
    this.status = OrderStatus.PAID;
    this.events.add(new OrderPaidEvent(this.id, this.userId));
}

// 营销上下文的应用服务
@Component
public class CouponListener {
    @EventListener
    public void on(OrderPaidEvent event) {
        // 营销自己的逻辑：给用户发券
        couponService.issueCoupon(event.getUserId(), CouponType.ORDER_PAID);
    }
}
```

## 你拿到新 PRD 后，个人实战的完整流程，就一个半小时的事

1.  **读 PRD**，用笔划出所有你觉得重要的名词和动词。（15分钟）
2.  **打开一个 Markdown 文件**，先写下 **“本次需求通用语言”** 部分，记下那些关键术语和你确认的代码命名。（10分钟）
3.  **用三个问题划上下文**，在文件里写下“上下文清单”和它们各自的职责一句话。（15分钟）
4.  **确定上下文之间怎么协作**，是建防腐层、还是拉共享内核、还是用事件。直接在清单旁边标注。（20分钟）
5.  **开始写代码**，严格按你划的边界建包。`com.xxx.order` 里绝对不出现 `com.xxx.logistics` 的类，跨边界操作永远通过你刚刚确定的协作方式走。（30分钟）

**实际意义：**
-   **不再怕需求变化**：需求改物流部分，你只碰 `logistics` 包，绝对不改订单核心代码，心里的踏实感就是战略设计给的。
-   **代码即文档**：新人来了，你让他看你那个 Markdown 词汇表和上下文清单，再配合代码包结构，他一天就能上手，不需要你来回来去解释。
-   **拒绝大泥球**：每个包都小，每个类都职责单一，这就是界限上下文在代码层的落地。没有花哨的工具，但你已经做得比 90% 的人都强。

你那份词汇表和上下文清单，加上你的战术代码，就是一套完整的、属于你自己的轻量级 DDD 实战体系。面试时你拿出这套东西，底气足得不是一点半点。

# Distributed Transaction (分布式事务)

### 📌 名词定义

Distributed Transaction（分布式事务）是指**跨越多个独立资源管理器（如多个数据库、消息队列）的事务操作，必须保证原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）和持久性（Durability）。是分布式系统中最复杂的挑战之一。**

### 🧠 第一性原理

"跨多个系统的操作，要么全成功，要么全失败。"
单体数据库的事务通过 ACID 保证，但分布式系统涉及多个独立的资源管理器，无法使用传统的本地事务。
**本质挑战：如何在保证数据一致性的同时，不牺牲系统的可用性和性能？**

### 🛠️ 落地实现（核心模式）

```
Distributed Transaction 的核心模式：

1. 强一致方案（CP）
   - [[Two-Phase Commit (两阶段提交：2PC)|两阶段提交（2PC/XA）]]：通过协调者统一指挥
   - 三阶段提交（3PC）：改进 2PC，减少阻塞
   - Seata AT 模式：改进的 2PC，异步提交
   - 优点：强一致；缺点：性能差，可用性低

2. 最终一致方案（AP）
   - [[Compensating Transaction (补偿事务)|Saga 模式]]：拆分为多个本地事务，失败时执行补偿
   - TCC (Try-Confirm-Cancel)：业务层面的两阶段提交
   - 本地消息表（Outbox Pattern）：通过消息队列保证最终一致
   - 事务消息（RocketMQ）：通过半消息保证最终一致
   - 优点：高性能，高可用；缺点：存在中间状态

3. 典型应用
   - 电商下单：创建订单 + 扣减库存 + 扣减余额
   - 跨行转账：A 银行扣款 + B 银行加款
   - 微服务调用：订单服务 + 库存服务 + 积分服务

4. 选择原则
   - 金融核心系统：优先强一致（2PC/Seata）
   - 互联网应用：优先最终一致（Saga/Outbox）
   - 跨组织系统：优先最终一致（事务消息）
```

### ⚖️ 架构权衡

- **优点**：保证跨系统数据一致性；支持复杂的业务流程。
    
- **缺点**：实现复杂，性能开销大；强一致方案可用性低，最终一致方案存在中间状态。
    
- **大厂实践**：阿里巴巴 Seata 提供多种分布式事务模式；蚂蚁金服使用 Saga 模式处理长事务；美团使用 RocketMQ 事务消息保证最终一致。

# Conflict Resolution & LWW (冲突解决与最后写入获胜)

### 📌 名词定义

Conflict Resolution（冲突解决）是指**在多主复制或最终一致性系统中，当多个节点并发写入同一数据时，如何合并冲突的写入。Last Write Wins (LWW) 是最简单的冲突解决策略，通过比较时间戳，保留最新的写入。**

### 🧠 第一性原理

"多个老板同时拍板，听谁的？"  
在多主复制或 [[AP System (AP 系统)|AP 系统]]中，并发写入是常态。  
**本质问题：如何在不协调的情况下，自动解决冲突？**

### 🛠️ 落地实现（核心策略）

```
Conflict Resolution & LWW 的核心策略：

1. Last Write Wins (LWW)
   - 每个写入附带时间戳
   - 合并时保留时间戳最新的写入
   - 优点：实现简单，无需协调
   - 缺点：可能丢失重要数据；依赖全局时钟同步

2. 自定义合并函数
   - 业务逻辑决定如何合并冲突
   - 例如：计数器取最大值、字符串取最长、集合取并集
   - 优点：可以保留所有写入的信息
   - 缺点：需要业务方参与设计

3. [[CRDT (无冲突复制数据类型)|CRDT]] (无冲突复制数据类型)
   - 通过数学结构保证合并无冲突
   - 例如：G-Counter（只能递增）、OR-Set（可增删）
   - 优点：天然支持并发，无需冲突解决
   - 缺点：数据结构复杂，实现难度大

4. 人工解决
   - 检测到冲突后，提示用户手动选择
   - 例如：Git 合并冲突、Google Docs 提示
   - 优点：最灵活，可以处理复杂场景
   - 缺点：用户体验差，需要人工干预

5. 典型应用
   - Cassandra：通过 LWW 解决多副本冲突
   - DynamoDB：通过 [[Vector Clock (向量时钟)|Vector Clock]] 检测冲突，LWW 解决
   - CouchDB：通过 Revision Tree 保留历史，LWW 解决冲突
   - Google Docs：通过 [[CRDT (无冲突复制数据类型)|CRDT]] 实现无冲突协同编辑
```

### ⚖️ 架构权衡

- **优点**：无需中心协调，自动解决冲突；适合高并发、离线优先的场景。
    
- **缺点**：LWW 可能丢失数据；CRDT 实现复杂；人工解决用户体验差。
    
- **大厂实践**：Cassandra、DynamoDB 使用 LWW 解决冲突；Google Docs、Figma 使用 CRDT 实现无冲突协同编辑。

# Saga 模式 (Saga Pattern - 补偿事务模型)

### 📌 名词定义

Saga 模式是指**将一个跨越多个微服务的长生命周期事务（Long-Running Process），拆分为一系列本地事务。每个本地事务在执行成功后立即提交并释放锁。如果后续的某一步骤发生失败，Saga 协调器会按照相反的顺序，依次调用前面已经成功步骤所对应的“补偿（Compensating）”事务来撤销影响。**

### 🧠 第一性原理

“先斩后奏，不行再退。”  
它打破了 2PC 锁住所有数据库的强一致枷锁，**允许数据在中间状态处于“非一致（软状态）”**。  
通过将一个长事务变成一个“多米诺骨牌链”，利用**逆向多米诺（补偿事务）**来达到最终的业务回滚。

### 🛠️ 落地实现（协同式 Saga / Choreography-based Saga）

在微服务场景下，通过**事件驱动**来实现无中心协调器的 Saga：

codeText

```
[订单服务] ──(订单创建事件)──> [库存服务] ──(库存扣减成功事件)──> [积分服务] (扣减失败！)
   │                                                               │
   │ <──(逆向库存补偿事件: 释放库存) ───────────────────────────────┤ (触发回滚链)
   │
   v (逆向订单补偿事件: 标记订单失效)
```

1. **正向执行**：
    
    - 步骤 A：OrderService 创建订单（本地 Commit）。
        
    - 步骤 B：InventoryService 扣减库存（本地 Commit）。
        
    - 步骤 C：CreditService 扣减积分。若失败，抛出异常。
        
2. **逆向补偿**：
    
    - CreditService 广播 CreditDeductFailedEvent。
        
    - InventoryService 监听该事件，执行 **补偿 SQL**：UPDATE stock = stock + ? [1.1.2]。
        
    - OrderService 监听该事件，执行 **补偿 SQL**：UPDATE order SET status = 'CANCELLED'。
        

### ⚖️ 架构权衡

- **优点**：支持长生命周期的业务流程；并发性能极高，没有全局物理锁，每个微服务能独立极速释放连接池。
    
- **缺点**：**缺乏“隔离性 (Isolation)”**。由于中间步骤已经 Commit，其他事务会读到未完全完成的数据（脏读）。
    
- **大厂实践**：极度适用于跨越多个部门、多个三方系统的超长链路流程（如：预订机票

### ⚠️ 开发踩坑点

- **空补偿大坑（Empty Compensation）**：由于网络丢包，正向操作还没执行（甚至没到达），逆向补偿先到了。库存服务收到 unlock 时，数据库里根本没有锁定记录。
    
    - 解法：补偿操作必须支持“幂等性”，且在找不到原记录时，必须静默返回成功，绝对不能报错挂起。
        
- **悬挂大坑（Pending Execution）**：正向操作网络延迟，逆向补偿先执行完了，正向操作才慢吞吞地到达。结果在补偿之后，又执行了正向修改，导致数据彻底脏掉。
    
    - 解法：在执行正向操作前，先校验该业务流水是否已经被补偿过。

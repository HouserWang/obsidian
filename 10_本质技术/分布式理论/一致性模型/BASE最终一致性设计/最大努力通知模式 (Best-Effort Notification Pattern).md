# 最大努力通知模式 (Best-Effort Notification Pattern)

### 📌 名词定义

最大努力通知模式是指**当发起方执行完状态变更后，通过一定的重试机制（通常是衰退性时间间隔，如 1s, 5s, 10s, 30s, 1m, 2h...），尽可能多地向接收方发送通知，直到接收方应答（ACK）或达到最大重试上限；同时，发起方必须提供一个“主动查询接口”，供接收方在通知丢失时主动校对状态。**

### 🧠 第一性原理

“我尽最大努力告诉你。如果你没听到，责任在你，但你可以随时来问我。”  
它将数据一致性的“高可用和低损耗”放在首位，通过**“多次重试 + 接收方主动拉取（Pull）”**的防线重组，用极低的基础设施成本解决跨系统的一致性。

### 🛠️ 落地实现（典型场景：三方支付回调，如微信/支付宝支付通知）

codeText

```
[三方支付系统] ──── 1. 异步通知 (Wechat/Alipay Notification) ───> [我们的商户系统]
       │                                                                │
       │  (如果网络抖动，商户系统未返回 SUCCESS)                          │
       │                                                                │
       ├──── 2. 衰退性重试通知 (10s, 30s, 5m, 2h...) ──────────────────>│
       │                                                                │
       │                                                    (还是失败或直接丢包了)
       │                                                                │
  [三方支付系统] <── 3. 主动反向轮询查询 (GET /pay/status?out_trade_no) ── [商户定时任务对账]
```

1. **主动通知（推）**：  
    三方支付成功后，向商户推送回调。若商户未返回 SUCCESS，支付系统启动定时任务进行衰退性重试（例如：24小时内重试 15 次）。
    
2. **反向查询（拉）**：  
    商户系统自身起一个定时任务，扫描所有超过 10 分钟依旧是 WAIT_PAY（待支付）的订单，主动调用三方接口查询真实支付状态，进行状态对齐。
    

### ⚖️ 架构权衡

- **优点**：系统结构极度简单，极力保护了发起方（如支付系统）的吞吐量，不受接收方系统性能和网络Flaky的影响。
    
- **缺点**：存在时间窗口延迟，数据达成一致的时间取决于轮询和重试间隔。
    
- **适用场景**：跨组织、跨企业的外部系统对接（如：支付回调、物流单号下发、短信发送结果反馈）。
    

### ⚠️ 开发踩坑点

- **接收方不幂等**：接收方在收到重复通知时，多次执行业务逻辑（如重复给用户加积分）。
    
    - 解法：接收方在执行通知逻辑前，**必须**使用唯一的“交易单号”建立防重表或加分布式锁。

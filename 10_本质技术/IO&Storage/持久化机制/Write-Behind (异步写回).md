# Write-Behind (异步写回)

### 📌 名词定义

Write-Behind（异步写回）是指**一种写入传播策略。数据先写入当前层级并立即返回，后台异步写入下一层级。追求高性能，但可能丢失数据。**

### 🧠 第一性原理

"先返回，后台写。"  
同步写两级存储性能太差，能否先返回用户，后台慢慢同步？  
**本质策略：通过异步写入下一级存储，极大提升写入性能，但承担数据丢失的风险。**

### 🛠️ 落地实现（核心机制）

```
Write-Behind 的核心机制：

1. 缓存场景
   - 写入缓存后立即返回成功
   - 后台异步批量写入数据库
   - 优点：性能极高
   - 缺点：缓存故障时数据丢失

2. 存储场景
   - 写入内存后立即返回
   - 后台异步批量刷盘
   - 类似异步刷盘（Async Flush）
   - 优点：性能极高
   - 缺点：断电时可能丢失未刷盘的数据

3. 典型应用
   - Redis 缓存：写入 Redis 后立即返回，异步写入数据库
   - 数据库 Buffer Pool：写入内存后立即返回，异步刷盘
   - Kafka Page Cache：写入 Page Cache 后立即返回，依赖 OS 刷盘

4. 对比 [[Write-Through (同步写穿)|Write-Through]]
   - Write-Behind：先写当前层，异步写下一层，高性能，可能丢数据
   - Write-Through：同步写两级，强一致，性能低

5. 核心优势
   - 性能极高：写入延迟极低
   - 批量写入：减少磁盘 IO 次数
   - 适合高并发场景
```

### ⚖️ 架构权衡

- **优点**：性能极高，写入延迟低；批量写入减少 IO 开销。
    
- **缺点**：可能丢失数据（缓存故障或断电）；数据一致性有延迟。
    
- **大厂实践**：Redis 缓存、Kafka Page Cache、数据库 Buffer Pool 都采用 Write-Behind 策略，追求极致性能。

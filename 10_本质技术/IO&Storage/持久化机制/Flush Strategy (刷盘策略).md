# Flush Strategy (刷盘策略)

### 📌 名词定义

Flush Strategy（刷盘策略）是指**数据何时从内存写入磁盘的本地持久化策略。包括同步刷盘（写入后等待磁盘确认）和异步刷盘（写入内存后返回，后台写入磁盘）。是 [[WAL (预写式日志)|WAL]] 的具体实现机制。**

### 🧠 第一性原理

"什么时候把内存数据落盘？"  
内存数据易失（断电丢失），磁盘数据持久但写入慢。  
**本质权衡：同步刷盘安全但慢，异步刷盘快但可能丢数据。**

### 🛠️ 落地实现（核心策略）

```
Flush Strategy 的核心策略：

1. 同步刷盘（Sync Flush）
   - 写入后立即调用 fsync() 强制落盘
   - 等待磁盘确认后才返回成功
   - 优点：数据极安全，断电不丢
   - 缺点：性能极差（fsync 是同步阻塞操作）
   - 典型应用：金融系统、RocketMQ SYNC_FLUSH

2. 异步刷盘（Async Flush）
   - 写入内存（Page Cache）后立即返回
   - 后台线程定期批量刷盘
   - 优点：性能极高（内存写入 + 批量磁盘 IO）
   - 缺点：断电时可能丢失未刷盘的数据
   - 典型应用：大多数系统默认策略

3. 定时刷盘 vs 定量刷盘
   - 定时：每隔 N 毫秒刷一次（如 1 秒）
   - 定量：内存达到 N MB 时刷盘
   - 混合：定时 + 定量，取两者之优

4. 典型应用
   - MySQL：异步刷盘，通过 Redo Log 保证持久性
   - Redis：AOF 支持 always（同步）、everysec（异步）、no（OS 决定）
   - RocketMQ：支持 SYNC_FLUSH 和 ASYNC_FLUSH
   - Kafka：依赖 OS Page Cache，不主动刷盘

5. 与其他概念的关系
   - 刷盘策略是 [[WAL (预写式日志)|WAL]] 的具体实现机制
   - 同步刷盘向 CP 靠拢，异步刷盘偏 AP
   - 刷盘策略 + [[Replication Strategy (复制策略)|复制策略]] = 完整的持久性保证
```

### ⚖️ 架构权衡

- **优点**：同步刷盘保证数据不丢失；异步刷盘性能极高。
    
- **缺点**：同步刷盘性能差；异步刷盘可能丢数据。
    
- **大厂实践**：MySQL、Kafka 采用异步刷盘 + 主从复制保证数据安全；RocketMQ 提供 SYNC_FLUSH 选项满足金融级需求；Redis AOF 提供三种刷盘策略供业务选择。

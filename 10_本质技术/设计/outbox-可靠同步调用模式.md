**“可靠同步调用模式（Reliable Synchronous Call / 同步双轨制）”。以下是三个最经典的落地花式技巧：

#### 技巧 1：同/异步双轨制（极速同步响应 + 异步对账保底）

- **痛点**：用户购买了虚拟商品（如话费充值、会员卡券），希望点击支付后**立刻拿到充值结果（必须同步调用三方接口，不能等异步 MQ 慢慢跑）
    
- **花式设计**：
    
    1. **在事务内（同步）**：保存业务数据 + 插入 outbox_event (状态为 PENDING)。**事务提交（COMMIT）。**
        
    2. **在事务提交后（立即同步调用）**：利用 Spring 事务同步器（afterCommit），立即向外部系统发起**同步的 HTTP/RPC 请求**。
        
        - **情况 A（99% 概率成功）**：RPC 成功，接收到响应，**当场将 outbox_event 物理删除/标记成功**。
            
        - **情况 B（1% 概率超时或网络抖动）**：RPC 发生超时，抛出异常。
            
    3. **定时任务介入（异步保底）**：定时任务扫描 outbox_event 表中仍处于 PENDING 状态、且已创建超过 30 秒的记录，**再次发起同步 RPC 补充调用**。
        
- **秒处**：**它兼顾了“同步调用”的低延迟体验（Happy Path 一步到位），又拥有“Outbox”的绝对可靠性（网络一抖，保底机制自动重试）。
    

#### 技巧 2：单体多模块“本地同步中转”（0 基础设施依赖，全靠内存）

在多模块单体（Modular Monolith）架构中，我们不需要部署 Kafka/RabbitMQ，但我们依然想让“订单模块”和“库存模块”可靠解耦。

- **花式设计**：
    
    1. 订单事务提交后，触发 afterCommit，直接**同步调用**库存模块公开的 Java 接口（inventoryService.deductStock()。
        
    2. 如果库存模块处理时发生了 Bug 或者临时锁等待，调用失败抛出异常。
        
    3. 订单服务的本地定时任务在 1 分钟后捞起该 outbox 记录，**再次同步调用**库存 Java 接口，直到扣减成功。
        
- **妙处**：**用纯内存方法调用，实现了完美的、强一致的消息防丢保护，全过程没有使用任何 MQ 队列，运维成本极低。
    

#### 技巧 3：面向不可逆三方接口的“可靠同步投递”

有些外部接口是不可逆的（比如调用国税局开具电子发票，你无法用 MQ 广播去开票，必须同步请求并拿到发票 PDF 下载地址）。

- **花式设计**：
    
    1. 业务事务提交，生成“发票草稿”，插入 outbox
        
    2. 专门的 InvoiceSyncService（开票同步服务）不断从 outbox 表里拿到任务，**排队、限流、同步调用**国税局接口。
        
    3. 因为国税局接口极慢，通过 Outbox 缓冲，既保护了我们自己的主交易流程不会被国税局接口拖垮，又保证了“发票最终一定能开出来”。
